#### 다형적(polymorphic) 파일 업로드 폼

**2026.02 – 2026.03** · 신규 기능 리드

사용자가 선택한 **타입에 따라 필수 입력값·허용 확장자·파일 파싱 방식이 전부 달라지는** 등록 폼입니다.
지원 타입이 6종이고 각 타입의 규격이 서로 겹치지 않아, 단순 조건 분기로는 유지보수가 불가능한 구조였습니다.

**타입별 규격을 설정으로 분리** — 타입마다 필드 구성 자체가 다르므로, 분기문 대신 선언형 설정 테이블에서
렌더링·검증·전송 페이로드를 결정하도록 했습니다. 타입 추가 시 기존 코드를 건드리지 않고 확장할 수 있습니다.

```js
const TYPE_CONFIG = {
  typeA: {
    upload: { maxFiles: 2, accept: '.aa,.xml' },
    parser: {
      match: (fileName) => /\.(aa|xml)$/i.test(fileName),
      parse: async (file) => parseDocument(file),   // 문서 내부에서 식별자 추출
    },
  },
  typeB: {
    upload: { maxFiles: 1, accept: '.bb' },
    parser: {
      match: (fileName) => /\.bb$/i.test(fileName),
      parse: (file) => parseFileName(file.name),    // 파일명 규격에서 추출
    },
  },
  typeC: { upload: { maxFiles: 1, accept: '.cc' } }, // 파서 없음
};

const REQUIRED_FIELDS_BY_TYPE = {
  typeA: ['source', 'files', 'groupKey', 'itemKey', 'version'],
  typeB: ['source', 'files', 'name', 'version', 'variant'],
  typeC: ['source', 'files', 'name', 'version'],
};
```

**비동기 파싱 결과의 경합(race condition) 해결** — 업로드한 파일을 클라이언트에서 파싱해 폼을 자동 완성하는데,
파싱이 비동기라 사용자가 타입을 바꾸거나 파일을 다시 고르면 **이전 요청의 결과가 뒤늦게 도착해 현재 폼을 덮어썼습니다.**
요청마다 시퀀스 번호를 발급하고, 완료 시점에 자신이 최신인지 확인해 낡은 결과를 폐기합니다.

```js
const parseSequenceRef = useRef(0);

const handleFileChange = async (name, files) => {
  const sequence = ++parseSequenceRef.current;   // 이번 요청의 번호 선점
  setFormValue((prev) => ({ ...prev, [name]: files }));

  const parser = TYPE_CONFIG[selectedType]?.parser;
  const target = files?.slice().reverse().find((f) => parser?.match(f.name));
  if (!target) return resetParsedValue();

  const parsed = await parser.parse(target);

  // 파싱 도중 타입 변경·파일 재선택이 있었다면 이 결과는 이미 낡음 → 폐기
  if (sequence !== parseSequenceRef.current) return;

  setFormValue((prev) => ({ ...prev, ...parsed }));
};
```

**자동 완성값과 검증 상태의 충돌** — 파서가 채운 값은 "검증 통과"로 봐야 제출이 가능한데,
통과로 고정하면 사용자가 그 값을 수정해도 재검증이 돌지 않았습니다.
검증 상태를 3-state로 모델링해 두 요구를 동시에 만족시켰습니다.

```js

const DIRTY = 'dirty';
const isPassed = (status) => status === true || status === DIRTY;

const getNextStatus = ({ previousStatus, value }) => {
  const hasValue =
    typeof value === 'string' ? value.trim().length > 0 : value != null;

  if (!hasValue) return false;                     // 비우면 무조건 미통과
  return isPassed(previousStatus) ? DIRTY : false; // 통과 이력이 있으면 dirty로 전이
};

const isSubmittable = ({ formValue, selectedType, validationState }) =>
  hasRequiredValues(formValue, selectedType) &&
  (REQUIRED_FIELDS_BY_TYPE[selectedType] ?? [])
    .every((field) => isPassed(validationState[field]));
```

**하위 폼 검증 집계** — 자식 폼들의 검증 핸들을 부모가 수집해 한 번에 실행합니다.
`Promise.all`이 아닌 `allSettled`를 써서 첫 실패에서 중단하지 않으므로, 사용자는 모든 오류를 한 번에 확인합니다.

```js
useImperativeHandle(ref, () => ({

    const handles = [
      sourceRef.current?.validate(),
      ...(config ? [uploadRef.current?.validate()] : []),
      fieldsRef.current?.validate(),
    ];
    return Promise.allSettled(handles).then((results) => {
      const rejected = results.filter((r) => r.status === 'rejected');
      if (rejected.length > 0) return Promise.reject(rejected[0].reason);
    });
  },
  getValue: () => buildPayloadByType(selectedType, formValue),
}));
```

#### 이종(heterogeneous) 이력 데이터의 타임라인

**2026.06 – 2026.07**

이력 종류가 4가지이고 **종류마다 응답 스키마가 완전히 다른** 것이 핵심 난점이었습니다.

**어댑터를 통한 뷰모델 정규화 + 의미 없는 이력 필터링** — 종류별 상세가 서로 다른 키에 다른 형태로 담겨 옵니다
(어떤 종류는 `~Before`/`~After` 접미사 필드, 어떤 종류는 중첩 객체).
공통 `before`/`after` 뷰모델로 변환해 렌더링 컴포넌트는 단일 형태만 알면 되게 했고,
변환 단계에서 값 변화가 없는 수정 이벤트를 걸러 타임라인 노이즈를 제거했습니다.

```js
const normalizeHistory = (rows) =>
  rows.reduce((acc, row) => {
    const base = { ...row, updatedAt: formatDateTime(row.updatedAt) };

    if (row.target === 'TYPE_A') {
      // 중첩 객체형: before/after가 이미 분리되어 옴
      const detail = row.typeADetail;
      return [...acc, { ...base, before: detail.before, after: detail.after }];
    }

    if (row.target === 'TYPE_B') {
      // 접미사형: 한 객체 안에 ~Before / ~After가 나란히 들어옴
      const d = row.typeBDetail;
      const before = { status: d.statusBefore, dueDate: d.dueDateBefore, memo: d.memoBefore };
      const after  = { status: d.statusAfter,  dueDate: d.dueDateAfter,  memo: d.memoAfter  };

      // 값이 하나도 안 바뀐 MODIFY는 보여줄 가치가 없음 → 제외
      const unchanged = Object.keys(before).every((k) => before[k] === after[k]);
      if (row.type === 'MODIFY' && unchanged) return acc;

      return [...acc, { ...base, before, after }];
    }

    return [...acc, { ...base, ...row.defaultDetail }];
  }, []);
```

패널을 닫을 때 캐시를 제거해, 다른 대상으로 재진입했을 때 **이전 대상의 이력이 잠깐 보이는 현상**을 없앴습니다.

#### 목록 갱신 — 필터를 유지하는 백그라운드 refetch

**2024.07 – 2025.10**

여러 단계의 승인을 거치는 업무 워크플로 화면군(요청 / 처리 대기 / 처리 완료 목록)을 담당했습니다.

**문제** — 항목을 처리하면 목록이 즉시 갱신되어야 하는데, `invalidateQueries`로 전체를 무효화하면
로딩 스피너가 뜨고 화면이 깜빡였습니다. 사용자가 처리 직후 목록의 필터·스크롤 맥락을 잃는 것이 특히 문제였습니다.

**해결** — 현재 마운트된 목록의 queryKey에서 **적용 중인 필터를 역추출**해 같은 조건으로 백그라운드 재조회한 뒤,
결과를 캐시에 직접 주입합니다. 로딩 상태를 거치지 않으므로 목록이 그 자리에서 조용히 갱신됩니다.

```js
const FETCHER_BY_VARIANT = {
  REQUESTED:  fetchRequestedList,
  TO_PROCESS: fetchToProcessList,
  PROCESSED:  fetchProcessedList,
};

const refreshListInPlace = async (queryClient) => {
  // 지금 화면에 떠 있는 목록 쿼리를 찾는다
  const [entry] = queryClient.getQueriesData({ queryKey: ['list'], stale: true });
  if (!entry) return;

  // queryKey 자체가 필터를 담고 있으므로 여기서 되꺼낸다
  const [, variant, filter] = entry[0];
  const fetchList = FETCHER_BY_VARIANT[variant];
  if (!fetchList) return;

  // 같은 조건으로 다시 받아 캐시에 직접 주입 → invalidate 없이 무깜빡임 갱신
  const result = await fetchList(filter)();
  queryClient.setQueryData(['list', variant, filter], result);
};
```

같은 패턴이 필요한 5개 목록 도메인에 동일한 형태로 적용해, "액션 후 목록 갱신"을 팀 내 일관된 방식으로 정착시켰습니다.

```js
const handleAuthError = (request, reply, err, user) => {

      return reply.code(401).send();

    const { redirect } = request.query ?? {};
    return reply.redirect(`/login${redirect ? `?redirect=${redirect}` : ''}`, 301);
  }
  request.user = user;
};

fastify.all('/auth/external', {
  preValidation: passport.authenticate('EXTERNAL', handleAuthError),

  await removePreviousSession(request, request.user); // 중복 로그인 방지
  return reply.redirect(request.query?.redirect ?? '/home', 301);
});
```

#### 대용량 트리 뷰의 지연 로딩

**2023.11**

파일·디렉터리 구조를 탐색기 형태로 보여주는 트리 뷰입니다.
노드가 수만 개에 달해 **전체 트리를 한 번에 받으면 응답에 수 초가 걸리고 메모리도 감당이 안 되는** 상황이었습니다.
GraphQL 조회 계층을 설계해 "필요한 깊이만 그때그때 받는" 구조로 바꿨습니다.

**루트 조회와 하위 조회의 분리** — 진입 시에는 최상위 노드만 받고, 사용자가 노드를 펼칠 때
해당 노드의 하위를 별도 쿼리로 가져옵니다. 초기 로딩 비용이 트리 전체 크기와 무관해집니다.

```js
// ① 진입 시: 최상위 노드만
export const fetchTreeRootNodes = (scopeKey) => async () => {
  const { result } = await requestGQL(gql`
    query fetchRootNodes($scopeKey: String!) {
      result: fetchRootNodes(scopeKey: $scopeKey) {
        id  name  parentId
        isParent          # 펼침 가능 여부를 서버가 판정해 내려줌
        hasFlag           # 하위에 주목할 항목이 있는지 (뱃지 표시용)
        children { id name parentId isParent }  # 한 단계 미리 받아 첫 펼침을 즉시 처리
      }
    }`, { scopeKey });
  return result;
};

// ② 노드를 펼칠 때: 그 노드의 하위만
export const fetchSubTree = async ({ scopeKey, parentId }) => {
  const { result } = await requestGQL(gql`
    query fetchSubTree($scopeKey: String!, $parentId: Long!) {
      result: fetchSubTree(scopeKey: $scopeKey, parentId: $parentId) {
        id  name  parentId  isParent
        children { id name parentId isParent isLeaf }
      }
    }`, { scopeKey, parentId });
  return result;
};
```

**확장 가능 여부를 서버가 판정** — 클라이언트가 "이 노드에 자식이 있나"를 알려면
원래는 자식을 미리 조회해봐야 합니다. 응답 스키마에 `isParent` / `isLeaf` 플래그를 포함시켜,
**펼침 화살표를 그리기 위한 목적만의 조회를 없앴습니다.**

**한 단계 선행 로딩** — 각 조회가 노드와 그 자식까지 1-depth를 함께 반환하도록 설계했습니다.
이미 받아둔 자식을 펼칠 때는 네트워크 왕복 없이 즉시 열리고, 더 깊이 들어갈 때만 요청이 나갑니다.
"매번 요청"과 "전부 미리 받기" 사이의 절충점입니다.

**검색은 트리가 아닌 평면 목록으로** — 검색 결과를 트리 형태로 복원하려면 매칭된 모든 노드의
조상 경로를 재구성해야 해 비용이 큽니다. 검색은 페이지네이션이 붙은 **평면 목록**으로 응답받아
무한 스크롤로 렌더링하고, 사용자가 항목을 선택한 시점에만 조상 경로를 조회해
트리에서 그 위치를 펼쳐 보여주는 방식으로 나눴습니다.

```js
// 검색: 트리 구조 없이 평면 목록 + 페이지네이션
export const searchNodes = async ({ scopeKey, keyword, pageNum, pageSize }) => {
  const { result } = await requestGQL(gql`
    query searchNodes($scopeKey: String!, $keyword: String!, $filter: NodeFilter!) {
      result: searchNodes(scopeKey: $scopeKey, keyword: $keyword, filter: $filter) {
        list { id name type isParent hasFlag }
        page  size  total  filtered
      }
    }`, {
    scopeKey,
    keyword,
    filter: { page: { page: pageNum, size: pageSize }, sorts: [{ key: 'id', order: 'asc' }] },
  });
  return result;
};

// 선택한 항목에 한해 조상 경로를 받아 트리를 그 지점까지 펼침
const revealInTree = async (nodeId) => {
  const path = await fetchAncestorPath({ scopeKey, childId: nodeId });
  setExpandedKeys((prev) => [...new Set([...prev, ...path])]);
};
```

담당 범위는 트리 조회 계층 설계와 지연 로딩 연동이며, 트리 렌더링 컴포넌트는 팀원과 협업했습니다.

#### 개발 인프라 개선

**라이브러리 메이저 마이그레이션 대응 — `useQueryEffects`**

TanStack Query v5에서 제거된 `onSuccess`/`onError`/`onSettled` 콜백을 대체하는 훅을 직접 구현했습니다.
단순히 `useEffect`로 옮기면 **리렌더마다 콜백이 재실행되는** 문제가 있어,
직전 상태를 기억해 성공/실패로 **전이하는 순간에만 1회** 실행되도록 했습니다.
제네릭 타입을 유지해 호출부의 데이터 타입 추론이 끊기지 않습니다.

```ts
export function useQueryEffects<TData, TError>(
  query: UseQueryResult<TData, TError>,
  { onSuccess, onError }: QueryEffectsOptions<TData, TError>,
) {
  const prevRef = useRef({ isSuccess: false, isError: false });

  useEffect(() => {
    const { isSuccess, isError, data, error } = query;
    const prev = prevRef.current;

    // 이미 성공 상태였다면 재실행하지 않음 → "전이" 시점에만 1회
    if (isSuccess && onSuccess && !prev.isSuccess) onSuccess(data as TData);
    if (isError && onError && !prev.isError) onError(error as TError);

    prevRef.current = { isSuccess, isError };
  }, [query.isSuccess, query.isError, query.data, query.error, onSuccess, onError]);

  return query;
}
```

```tsx
useEffect(() => {
```
