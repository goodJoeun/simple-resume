#### 타입마다 규격이 다른 업로드 폼을 선언형 설정으로 분리했습니다.

사용자가 선택한 **타입에 따라 필수 입력값·허용 확장자·파일 파싱 방식이 전부 달라지는** 등록 폼입니다.
지원 타입이 6종이고 각 타입의 규격이 서로 겹치지 않아, 단순 조건 분기로는 유지보수가 불가능한 구조였습니다.

**타입별 규격을 설정으로 분리** — 타입마다 필드 구성 자체가 다르므로, 분기문 대신 선언형 설정 테이블에서
렌더링·검증·전송 페이로드를 결정하도록 했습니다. 타입 추가 시 기존 코드를 건드리지 않고 확장할 수 있습니다.

```js
const TYPE_CONFIG = {
  typeA: {
    upload: { maxFiles: 2, accept: '.aa,.xml' },
    parser: {
      match: (fileName) => /\.(aa|xml)$/i.test(fileName),
      parse: async (file) => parseDocument(file),   // 문서 내부에서 식별자 추출
    },
  },
  typeB: {
    upload: { maxFiles: 1, accept: '.bb' },
    parser: {
      match: (fileName) => /\.bb$/i.test(fileName),
      parse: (file) => parseFileName(file.name),    // 파일명 규격에서 추출
    },
  },
  typeC: { upload: { maxFiles: 1, accept: '.cc' } }, // 파서 없음
};

const REQUIRED_FIELDS_BY_TYPE = {
  typeA: ['source', 'files', 'groupKey', 'itemKey', 'version'],
  typeB: ['source', 'files', 'name', 'version', 'variant'],
  typeC: ['source', 'files', 'name', 'version'],
};
```

**비동기 파싱 결과의 경합(race condition) 해결** — 업로드한 파일을 클라이언트에서 파싱해 폼을 자동 완성하는데,
파싱이 비동기라 사용자가 타입을 바꾸거나 파일을 다시 고르면 **이전 요청의 결과가 뒤늦게 도착해 현재 폼을 덮어썼습니다.**
요청마다 시퀀스 번호를 발급하고, 완료 시점에 자신이 최신인지 확인해 낡은 결과를 폐기합니다.

```js
const parseSequenceRef = useRef(0);

const handleFileChange = async (name, files) => {
  const sequence = ++parseSequenceRef.current;   // 이번 요청의 번호 선점
  setFormValue((prev) => ({ ...prev, [name]: files }));

  const parser = TYPE_CONFIG[selectedType]?.parser;
  const target = files?.slice().reverse().find((f) => parser?.match(f.name));
  if (!target) return resetParsedValue();

  const parsed = await parser.parse(target);

  // 파싱 도중 타입 변경·파일 재선택이 있었다면 이 결과는 이미 낡음 → 폐기
  if (sequence !== parseSequenceRef.current) return;

  setFormValue((prev) => ({ ...prev, ...parsed }));
};
```

**자동 완성값과 검증 상태의 충돌** — 파서가 채운 값은 "검증 통과"로 봐야 제출이 가능한데,
통과로 고정하면 사용자가 그 값을 수정해도 재검증이 돌지 않았습니다.
검증 상태를 3-state로 모델링해 두 요구를 동시에 만족시켰습니다.

```js
// true = 검증 통과 / false = 미통과 / 'dirty' = 통과 이력이 있으나 사용자가 수정함
const DIRTY = 'dirty';
const isPassed = (status) => status === true || status === DIRTY;

const getNextStatus = ({ previousStatus, value }) => {
  const hasValue =
    typeof value === 'string' ? value.trim().length > 0 : value != null;

  if (!hasValue) return false;                     // 비우면 무조건 미통과
  return isPassed(previousStatus) ? DIRTY : false; // 통과 이력이 있으면 dirty로 전이
};

const isSubmittable = ({ formValue, selectedType, validationState }) =>
  hasRequiredValues(formValue, selectedType) &&
  (REQUIRED_FIELDS_BY_TYPE[selectedType] ?? [])
    .every((field) => isPassed(validationState[field]));
```

#### 깜빡임 없이 목록이 갱신되도록 필터를 유지한 채 다시 받아왔습니다.

여러 단계의 승인을 거치는 업무 워크플로 화면군(요청 / 처리 대기 / 처리 완료 목록)을 담당했습니다.

**문제** — 항목을 처리하면 목록이 즉시 갱신되어야 하는데, `invalidateQueries`로 전체를 무효화하면
로딩 스피너가 뜨고 화면이 깜빡였습니다. 사용자가 처리 직후 목록의 필터·스크롤 맥락을 잃는 것이 특히 문제였습니다.

**해결** — 현재 마운트된 목록의 queryKey에서 **적용 중인 필터를 역추출**해 같은 조건으로 백그라운드 재조회한 뒤,
결과를 캐시에 직접 주입합니다. 로딩 상태를 거치지 않으므로 목록이 그 자리에서 조용히 갱신됩니다.

```js
const FETCHER_BY_VARIANT = {
  REQUESTED:  fetchRequestedList,
  TO_PROCESS: fetchToProcessList,
  PROCESSED:  fetchProcessedList,
};

const refreshListInPlace = async (queryClient) => {
  // 지금 화면에 떠 있는 목록 쿼리를 찾는다
  const [entry] = queryClient.getQueriesData({ queryKey: ['list'], stale: true });
  if (!entry) return;

  // queryKey 자체가 필터를 담고 있으므로 여기서 되꺼낸다
  const [, variant, filter] = entry[0];
  const fetchList = FETCHER_BY_VARIANT[variant];
  if (!fetchList) return;

  // 같은 조건으로 다시 받아 캐시에 직접 주입 → invalidate 없이 무깜빡임 갱신
  const result = await fetchList(filter)();
  queryClient.setQueryData(['list', variant, filter], result);
};
```

같은 패턴이 필요한 5개 목록 도메인에 동일한 형태로 적용해, "액션 후 목록 갱신"을 팀 내 일관된 방식으로 정착시켰습니다.




#### 대용량 데이터를 대상으로 성능 최적화를 이뤄냈습니다.

- 파일·디렉터리 구조를 탐색기 형태로 보여주는 트리 뷰입니다.
- 노드가 수만 개에 달해 **전체 트리를 한 번에 받으면 응답에 수 초가 걸리고 메모리도 감당이 안 되는** 상황이었습니다.
- GraphQL 조회 계층을 설계해 **지연 로딩(필요한 깊이만 그때그때 받는)** 구조로 바꿨습니다.

**루트 조회와 하위 조회의 분리** — 진입 시에는 최상위 노드만 받고, 사용자가 노드를 펼칠 때
해당 노드의 하위를 별도 쿼리로 가져옵니다. 초기 로딩 비용이 트리 전체 크기와 무관해집니다.

```js
// ① 진입 시: 최상위 노드만
export const fetchTreeRootNodes = (scopeKey) => async () => {
  const { result } = await requestGQL(gql`
    query fetchRootNodes($scopeKey: String!) {
      result: fetchRootNodes(scopeKey: $scopeKey) {
        id  name  parentId
        isParent          # 펼침 가능 여부를 서버가 판정해 내려줌
        hasFlag           # 하위에 주목할 항목이 있는지 (뱃지 표시용)
        children { id name parentId isParent }  # 한 단계 미리 받아 첫 펼침을 즉시 처리
      }
    }`, { scopeKey });
  return result;
};

// ② 노드를 펼칠 때: 그 노드의 하위만
export const fetchSubTree = async ({ scopeKey, parentId }) => {
  const { result } = await requestGQL(gql`
    query fetchSubTree($scopeKey: String!, $parentId: Long!) {
      result: fetchSubTree(scopeKey: $scopeKey, parentId: $parentId) {
        id  name  parentId  isParent
        children { id name parentId isParent isLeaf }
      }
    }`, { scopeKey, parentId });
  return result;
};
```

**확장 가능 여부를 서버가 판정** — 클라이언트가 "이 노드에 자식이 있나"를 알려면
원래는 자식을 미리 조회해봐야 합니다. 응답 스키마에 `isParent` / `isLeaf` 플래그를 포함시켜,
**펼침 화살표를 그리기 위한 목적만의 조회를 없앴습니다.**

**검색은 트리가 아닌 flat data로** — 검색 결과를 트리 형태로 복원하려면 매칭된 모든 노드의
조상 경로를 재구성해야 해 비용이 큽니다. 검색은 페이지네이션이 붙은 **flat한 데이터**로 응답받아
무한 스크롤로 렌더링하고, 사용자가 항목을 선택한 시점에만 조상 경로를 조회해
트리에서 그 위치를 펼쳐 보여주는 방식으로 나눴습니다.

```js
// 검색: 트리 구조 없이 평면 목록 + 페이지네이션
export const searchNodes = async ({ scopeKey, keyword, pageNum, pageSize }) => {

      result: searchNodes(scopeKey: $scopeKey, keyword: $keyword, filter: $filter) {
        list { id name type isParent hasFlag }
        page  size  total  filtered
      }
    }`, {
    scopeKey,
    keyword,
    filter: { page: { page: pageNum, size: pageSize }, sorts: [{ key: 'id', order: 'asc' }] },
  });
  return result;
};

// 선택한 항목에 한해 조상 경로를 받아 트리를 그 지점까지 펼침
const revealInTree = async (nodeId) => {
```

#### 마이그레이션 대응 훅과 상태 보존형 mock으로 개발 환경을 정비했습니다.

**라이브러리 메이저 마이그레이션 대응 — `useQueryEffects`**

- TanStack Query v5에서 제거된 `onSuccess`/`onError`/`onSettled` 콜백을 대체하는 훅을 직접 구현했습니다.
- 단순히 `useEffect`로 옮기면 **리렌더마다 콜백이 재실행되는** 문제가 있어, 직전 상태를 기억해 성공/실패로 **전이하는 순간에만 1회** 실행되도록 했습니다.
- 제네릭 타입을 유지해 호출부의 데이터 타입 추론이 끊기지 않습니다.

```ts
export function useQueryEffects<TData, TError>(
  query: UseQueryResult<TData, TError>,
  { onSuccess, onError }: QueryEffectsOptions<TData, TError>,
) {
  const prevRef = useRef({ isSuccess: false, isError: false });

  useEffect(() => {
    const { isSuccess, isError, data, error } = query;
    const prev = prevRef.current;

    // 이미 성공 상태였다면 재실행하지 않음 → "전이" 시점에만 1회
    if (isSuccess && onSuccess && !prev.isSuccess) onSuccess(data as TData);
    if (isError && onError && !prev.isError) onError(error as TError);

    prevRef.current = { isSuccess, isError };
  }, [query.isSuccess, query.isError, query.data, query.error, onSuccess, onError]);

  return query;
}
```

- 기존 컴포넌트 대부분이 Emotion·전역 스토어·이벤트 핸들러에 의존하고 있었습니다.

- 기존 requestGQL은 axios 기반에 브라우저 쿠키·인터셉터·window 의존이 섞여 있어 RSC에서 호출할 수 없었습니다.

```diff
+ // utils/server/requestGQL.ts  — 신설 (RSC 전용)
+ import { cookies } from 'next/headers';
+
+ export async function requestGQLServer(query: string, variables?: Record<string, any>) {
+   // 브라우저가 없는 실행 컨텍스트이므로 세션 쿠키를 명시적으로 전달해
+   // 인증 컨텍스트를 서버 렌더 경로에서도 그대로 유지한다.
+   const cookieHeader = (await cookies())
+     .getAll()
+     .map((c) => `${c.name}=${c.value}`)
+     .join('; ');
+
+   const response = await fetch(`${INTERNAL_GATEWAY}/graphql`, {
+     method: 'POST',
+     headers: {
+       'Content-Type': 'application/json',
+       Cookie: cookieHeader,
+       'X-Internal-Call': 'true',
+     },
+     body: JSON.stringify({ query, variables }),
+     cache: 'no-store',       // 사용자별 인증 데이터이므로 캐시 금지
+   });
+
+   if (!response.ok) throw new Error(`GraphQL request failed: ${response.status}`);
+
+   const json = await response.json();
+   // GraphQL은 200 응답 안에 errors를 담으므로 명시적으로 throw
+   // → 상위 Promise.allSettled가 쿼리 단위로 격리
+   if (json.errors) throw new Error(`GraphQL errors: ${JSON.stringify(json.errors)}`);
+   return json.data;
+ }
```

응답 가공 로직을 클라이언트 버전과 **동일한 형태로 맞춰**, 서버 seed / 클라이언트 폴백 중 어느 경로로 채워져도 캐시에 들어가는 shape이 같도록 했습니다.

```diff
+ // utils/server/getSessionServer.ts
+ export async function getSessionServer() {
+   const { result } = await requestGQLServer(`{
+     result: selectCurrentUser {
+       user { id name email locale globalRoles { authorities { key } } }
+     }
+   }`);
+
+   // 클라이언트 버전과 동일한 평탄화 규칙을 적용해야
+   // 어느 경로로 채워져도 소비 코드가 동일하다.
+   const authorities = result.user.globalRoles
+     .flatMap((role) => role.authorities.map((a) => a.key))
+     .map((key) => `system-${key}`);
+
+   return { user: result.user, authorities };
+ }
```

#### 3단 요청 워터폴과 hydration 직후의 중복 요청을 제거했습니다.

**요청 워터폴 제거** — 대시보드는 초기 데이터 9개 + 본문 데이터 6개가 필요했는데, 클라이언트에서 순차·조건부로 호출해 3단 워터폴이 생겼습니다.

```diff
- // [Before] 클라이언트에서 순차·조건부 → 워터폴
- const { data: session } = useQuery(...);                       // 1단계
- const { data: projects } = useQuery({ enabled: !!session });   // 2단계 (세션 대기)
- const hasData = projects?.length > 0;
- const { data: summary } = useQuery({ enabled: hasData });      // 3단계 (판정 대기)

+ // [After] 서버에서 단일 배치로 병렬 발사
+ // 본문 데이터는 원래 "표시할 데이터가 있는가" 판정 이후에만 필요하지만,
+ // 판정을 기다리면 워터폴이 생기므로 투기적으로 함께 요청하고
+ // HTML에 직렬화할지만 조건부로 결정한다.
+ const [session, projects, summary, charts, items, recent, /* … */] =

+     getProjectsServer(),
+     getSummaryServer(bodyFilter),
+     getChartsServer(bodyFilter),
+     getVulnerableItemsServer(bodyFilter, bodyPage),
+     /* … 총 15개 */
+   ]);
+
+ // allSettled이므로 한 쿼리 실패가 페이지 전체를 무너뜨리지 않는다
+ if (session.status === 'fulfilled') {
+   queryClient.setQueryData(['session'], session.value.user);
+ }
```

```diff
+ const dehydratedState = useMemo(() => dehydrate(queryClient), [queryClient]);
```

#### route별 화면을 `dynamic import`로 분리했습니다.

**문제** — 조건부 렌더링은 렌더 결과만 하나로 줄이고, 번들러가 분석하는 모듈 그래프는 그대로 둡니다.
Pages Router의 `/personal`은 페이지 컴포넌트가 현재 화면 식별자를 `useState`로 관리하고, shallow routing과 조건문으로 여러 패널 중 하나를 렌더했습니다.
화면에는 한 패널만 나타났지만 상위 패널 컴포넌트가 다섯 패널을 모두 정적으로 import했으므로, 선택되지 않은 패널의 테이블·모달·훅까지 같은 페이지 모듈 그래프에 포함됐습니다.
App Router로 그대로 옮겨 최상단 패널에 `'use client'`를 붙여도 이 부분은 바뀌지 않습니다.
인증·초기 데이터 결정만 서버로 넘어가고, 화면 선택과 다섯 패널은 여전히 하나의 Client graph로 남습니다.

```
// Pages Router
pages/personal/index.js (Client)
  ├─ getServerSideProps: 세션 및 공통 캐시 준비
  ├─ useState: 현재 화면 식별자 관리
  └─ PersonalPanel: 5개 패널 정적 import 후 조건부 렌더링
```

**원인 확인** — 정적 import 여부 자체가 빌드 OOM의 재현 조건이었습니다.
App Router의 `PersonalPanel`에서 다섯 패널을 정적으로 import하는 실험을 했을 때 `server.js` Node 프로세스가 `--max_old_space_size=6144` 한도까지 증가해 OOM이 재현됐고, `dynamic import`를 복원하면 발생하지 않았습니다.
OOM 로그만으로 특정 컴파일러를 원인으로 확정할 수는 없었지만, **동일한 화면에서 정적 import 여부가 재현 조건을 바꾼다는 점**은 확인했습니다.
조건부 렌더링과 코드 스플리팅이 서로 다른 문제라는 근거로 삼아, 패널을 각각 독립된 chunk로 떼어내는 방향을 택했습니다.

**해결** — 패널마다 `dynamic import` boundary를 두고, Client Loader는 dispatch만 담당하게 했습니다.
Server Component가 페이지 진입과 초기 데이터를 책임지고, 하나의 Client Loader가 화면 식별자로 패널을 고르되 실제 패널 구현은 각각 독립된 chunk로 남습니다.
`PANEL_MAP`에 매핑을 모아둬서 패널이 늘어도 Loader의 분기가 아니라 map의 항목만 늘어납니다.

```diff
- // 하나의 Client Component가 실제 패널을 정적으로 import
- import FirstPanel from './panels/FirstPanelClient';
- import SecondPanel from './panels/SecondPanelClient';
- // 나머지 패널도 같은 Client graph에 포함

+ // PersonalPanelLoader.tsx ('use client')
+ const FirstPanel = dynamic(
+   () => import('../panels/FirstPanelClient'),
+   { ssr: false, loading: () => <Preloader type="inline" /> },
+ );
+ const SecondPanel = dynamic(
+   () => import('../panels/SecondPanelClient'),
+   { ssr: false, loading: () => <Preloader type="inline" /> },
+ );
+
+ const Panel = PANEL_MAP[selectedView] ?? PANEL_MAP.default;
+ return <Panel />;
```

```
PersonalPage (Server)
  ├─ 인증·권한·라이선스 조회
  ├─ 현재 화면의 데이터만 QueryClient에 seed
  └─ PersonalPanel (Server)
      └─ PersonalPanelLoader (Client)
          ├─ 화면 식별자 → Panel routing
          ├─ dynamic loading 중 Preloader 표시
          └─ 선택된 PanelClient chunk
```

**로딩 상태의 소유권 분리** — `dynamic.loading`의 `Preloader`는 데이터 요청 상태가 아니라 **패널 JavaScript chunk를 내려받고 평가하는 동안의 fallback**입니다.
데이터 refetch 상태는 패널 내부 `useQuery`의 `isLoading`·`isFetching`으로 별도 처리합니다.
코드 로딩과 데이터 로딩을 같은 spinner로 표현할 수는 있지만, 상태의 소유권은 구분했습니다.

**데이터 범위도 같은 기준으로** — 코드를 화면 단위로 자른 것과 같은 기준을 서버 prefetch에도 적용했습니다.
`/personal`은 URL query parameter로 선택된 화면에 따라 필요한 목록 API도 정확히 하나로 결정됩니다.
대시보드는 한 화면에 여러 위젯이 동시에 필요해 다수 쿼리를 병렬 prefetch했지만, 여기서 모든 화면을 미리 준비하는 것은 초기 응답 크기와 서버 부하만 늘립니다.

| 구분 | 기존 대시보드 마이그레이션 | `/personal` 마이그레이션 |
|---|---|---|
| 초기 화면 구성 | 여러 위젯이 동시에 필요 | 탭 하나만 필요 |
| 서버 조회 전략 | 독립 쿼리 다수를 병렬 prefetch | 선택된 탭의 목록 쿼리 하나만 prefetch |
| 상태 기준 | 필터 및 위젯별 queryKey | URL query parameter와 저장된 마지막 필터 |
| 코드 분할 | 화면 단위 Client boundary | 패널별 `dynamic import` boundary |
| 클라이언트 후속 동작 | 위젯별 refetch | 필터·정렬·페이지 변경 및 탭 이동 |

Pages Router에서는 선택된 화면 상태가 `useState`와 shallow routing으로 이중 관리됐습니다.
App Router에서는 `page.tsx`가 URL query parameter를 읽고 허용된 화면 식별자인지 검증한 뒤 기본 화면을 결정합니다.
인증 정보와 라이선스 제한은 서버에서 병렬 조회하고, 화면별 조회 설정 테이블에서 현재 화면의 API·queryKey·기본 정렬 조건을 선택합니다.
사용자가 마지막으로 사용한 필터가 있으면 기본값과 병합해 **현재 화면의 첫 페이지 데이터만** 조회합니다.

```diff
- // Pages Router: 클라이언트 상태와 URL을 함께 갱신
- const [selectedView, setSelectedView] = useState(initialView);
- router.push({ pathname, query: { [VIEW_PARAM]: nextView } }, newUrl, {
-   shallow: true,
- });
- setSelectedView(nextView);

+ // App Router: URL을 서버의 단일 기준으로 사용
+ const routeState = (await searchParams) ?? {};
+ const selectedView = resolveView(routeState);
+ const config = VIEW_QUERY_CONFIG[selectedView];
+
+ const [loginResult, licenseRestriction] = await Promise.all([
+   getLoginInfoServer(),
+   getLicenseRestrictionServer(),
+ ]);
+
+ const filter = getCachedFilter(
+   loginResult.lastFilters,
+   config.key,
+   config.filter,
+ );
+ const result = await config.fetch(filter); // 선택된 화면의 API만 호출
+ const queryKey = 'queryKey' in config ? config.queryKey : [config.key];
+ queryClient.setQueryData([...queryKey, filter], result);
```

이 설정 객체는 단순 기본값 모음이 아니라 **화면 식별자 → 캐시 키 → 기본 필터 → 서버 요청 함수**를 연결하는 dispatch table입니다.
조건문마다 API와 queryKey를 따로 관리하지 않아, 서버 prefetch와 클라이언트 `useQuery`가 동일한 필터·캐시 주소를 사용하도록 만들었습니다.

**서버 prefetch와 클라이언트 조회의 역할 분리** — 같은 캐시를 두 단계로 채웁니다.
패널의 `useQuery`는 제거하지 않았습니다. 서버가 `setQueryData` 후 `HydrationBoundary`로 전달한 캐시를 첫 렌더에서 읽고,
이후 필터·정렬·페이지 변경과 명시적 invalidate를 처리해야 하기 때문입니다.
서버는 초기 상태를 채우고 클라이언트 훅은 그 상태를 구독한다는 역할 분리입니다.

```
page.tsx
  └─ setQueryData([config.queryKey, filter], result)
      └─ dehydrate / HydrationBoundary
          └─ useQuery({ queryKey: [queryKey, filter], ... })
```

이 과정에서 `staleTime`의 의미도 확인했습니다. 현재 전역 설정에는 `staleTime`이 없으므로 기본값 `0`이 적용되고,
`refetchOnMount: true`와 결합되어 hydrated 데이터가 화면에 즉시 사용된 뒤 클라이언트에서 백그라운드 refetch가 발생할 수 있습니다.
즉 현재 구현은 **서버 응답으로 초기 로딩 상태를 제거하는 효과는 얻지만, 최초 중복 네트워크 요청까지 제거한 상태는 아닙니다.**
중복 요청을 제거하려면 `/personal`의 prefetch 대상 query에만 제한적으로 `staleTime`을 설정해야 하며, Pages Router 화면까지 영향을 주는 전역 변경은 피해야 합니다.

**결론** — 조건부 렌더링에 가려져 있던 코드 로딩 범위를 `dynamic import`로 실제로 잘라낸 사례입니다.
정적 import 실험에서 재현된 빌드 OOM을 근거로 **조건부 렌더링과 코드 스플리팅이 서로 다른 문제**라는 점을 확인했고,
서버 prefetch 대상을 API 단위로만 판단하지 않고 그 화면이 어떤 Client graph를 활성화하는지까지 함께 검증했습니다.
결과적으로 URL로 선택된 단일 탭에 대해 JavaScript 로딩 범위와 데이터 prefetch 범위를 같은 기준으로 제한했습니다.

### Atomic design 디자인시스템 라이브러리 개발

> Sparrow Enterprise를 포함해 사내 여러 제품이 공유하는 컴포넌트 라이브러리입니다.
> 하나의 컴포넌트가 여러 제품·화면에서 재사용되므로, 개별 화면 로직보다
> **범용적인 상태 모델링과 API 설계**, 그리고 **회귀 없는 변경**이 핵심 과제였습니다.

`React` `TypeScript` `Emotion` `Nx` `Yarn Workspaces` `Rollup` `Storybook` `react-dnd` `Changesets` `BackstopJS` `Playwright` `Docker`


#### 재사용 가능한 "동적 리스트" 아키텍처를 설계했습니다.

- 이슈 검출 규칙의 예시 코드 입력처럼, 항목을 자유롭게 추가·삭제·순서 변경하면서 전체를 한 번에 검증해야 하는 요구사항이 여러 화면에서 반복적으로 등장
  - 각 행은 자신의 값만 알고 있는데, 상위에서 "전체 제출"을 누르면 모든 행이 동시에 검증되어야 하는 문제
  - 각 행이 `useImperativeHandle`로 `validate()`를 노출하고, 리스트 컴포넌트가 ref 배열로 이를 수집해 `Promise.all`로 한 번에 실행하는 imperative 검증 API를 설계하여 해결
- `react-dnd`로 행을 드래그해 순서를 바꿀 때, 배열 값뿐 아니라 각 행이 들고 있는 ref도 같은 인덱스로 함께 재배치되지 않으면 검증 API가 엉뚱한 행을 가리키는 문제
  - `immutability-helper`의 `$splice`로 값 배열과 ref 배열을 항상 같은 트랜잭션에서 재정렬해 정합성을 유지하도록 처리
- 외부 `value`가 갱신될 때마다 매번 새 uuid를 부여하면 React key가 바뀌어 불필요한 리마운트(포커스 손실, 드래그 애니메이션 깨짐)가 발생하는 문제
  - 기존 인덱스에 대응하는 항목은 이전 id를 유지하고, 새로 추가된 항목에만 새 id를 부여하는 동기화 effect를 작성하여 해결
- Context 기반 compound component(`List.Footer`)로 "항목 추가" 트리거를 노출해, 사용하는 쪽에서 버튼 위치·문구를 자유롭게 커스터마이징할 수 있도록 API 설계
  - 같은 패턴을 이후 조치 우선순위 기준(`PriorityCriteria`) 컴포넌트에도 그대로 재사용하여 아키텍처의 범용성을 검증

```tsx
interface RowHandle {
  validate: () => Promise<void>;
}

const DynamicList = forwardRef((props: DynamicListProps, ref) => {
  const rowRefs = useRef<(RowHandle | null)[]>([]);
  const [items, setItems] = useState(
    props.value.map((v) => ({ ...v, key: generateId() })),
  );

  // 여러 행을 한 번에 검증하는 imperative API
  useImperativeHandle(ref, () => ({
    validate: () =>
      Promise.all(rowRefs.current.map((row) => row?.validate?.()))
        .then(() => Promise.resolve())
        .catch(() => Promise.reject()),
  }));

  // 드래그로 순서를 바꾸면 값 배열과 ref 배열을 같은 트랜잭션에서 재정렬
  const handleReorder = useCallback((fromIndex: number, toIndex: number) => {
    setItems((prev) => arrayMove(prev, fromIndex, toIndex));
    rowRefs.current = arrayMove(rowRefs.current, fromIndex, toIndex);
  }, []);

  // 외부 value가 갱신돼도 기존 항목의 key(id)는 유지 → 불필요한 리마운트 방지
  useEffect(() => {
    setItems((prev) =>
      props.value.map((next, i) => ({
        ...next,
        key: prev[i]?.key ?? generateId(),
      })),
    );
  }, [props.value]);

  return (
    <DndContext onReorder={handleReorder}>
      {items.map((item, i) => (
        <Row key={item.key} value={item} ref={(el) => (rowRefs.current[i] = el)} />
      ))}
    </DndContext>
  );
});
```

#### 무한 스크롤 이력 타임라인의 로딩 상태를 명시적으로 모델링했습니다.

- 이슈의 담당자·상태·의견·결재 요청·조치 계획 변경 이력을 시간순으로 보여주는 컴포넌트, 이력 종류가 5가지이고 종류마다 "변경 전/후" 데이터 스키마가 완전히 다른 것이 난점
  - 단순히 "화면에 보이면 로드"하는 방식 대신, 최초 마운트(`isInitial`) · 로딩 중(`isLoading`) · 더 이상 데이터 없음(`isDone`) 세 상태를 조합해 `IntersectionObserver`의 observe/unobserve를 제어
  - 로딩 중 중복 요청이나, 데이터가 끝났는데도 observer가 남아 불필요하게 재호출되는 문제를 방지
  - 5가지 변경 유형별로 표시할 diff 내용이 서로 달라, 유형에 따라 렌더링을 분기하는 Content 컴포넌트를 설계
- 결재/조치계획 상세로 이동하는 링크는 해당 리소스가 아직 살아있을 때만 노출해야 하는 요구사항 (삭제된 리소스로의 dead link 방지)
  - `isRequestAlive`/`isRemediationAlive` 플래그로 조건부 렌더링해 해결

```tsx
function useInfiniteScrollObserver(
  onReachEnd: () => void,
  state: { isInitial: boolean; isLoading: boolean; isDone: boolean },
) {
  const targetRef = useRef<HTMLDivElement>(null);
  const [observe, unobserve] = useIntersectionObserver(onReachEnd);

  useEffect(() => {
    if (state.isInitial) return;

    // 로딩 중이거나 더 이상 데이터가 없으면 관찰을 멈추고,
    // 그 외에만(대기 상태) 스크롤 끝 지점을 관찰한다
    if (state.isDone || state.isLoading) {
      unobserve(targetRef.current!);
    } else {
      observe(targetRef.current!);
    }
  }, [state.isInitial, state.isDone, state.isLoading]);

  return targetRef;
}

// 변경 유형(5종)마다 다른 스키마를 공통 뷰로 렌더링
function TimelineEntry({ type, before, after }: TimelineEntryProps) {
  const Content = CONTENT_BY_TYPE[type];
  return <Content before={before} after={after} />;
}
```


#### 컴포넌트의 타입별 중복 구현을 컴파운드 컴포넌트 패턴으로 리팩토링했습니다.

- 5가지 데이터 타입의 목록을 보여주는 테이블에서, 타입마다 레이아웃·페이지네이션·행 렌더링 로직이 통째로 중복된 독립 컴포넌트로 구현되어 공통 UI 하나를 고치려면 5곳을 각각 수정해야 하는 문제
  - `InformationTable`(타입에 따라 하위 Body를 스위칭하는 컨테이너) → `*InformationBody`(타입별 바디, 공통 `BodyWrapper`+`ResponsiveRow`+`Divider` 레이아웃 공유) → `*ListRow`(타입별 행, 실제 콘텐츠만 담당) 3단 계층으로 분리
  - 여러 타입에서 중복되던 `Suffix`, `TooltipParagraph` 등 UI 조각을 공통 컴포넌트로 추출
  - 순수 삭제 652줄 / 순수 추가 208줄 — 동일 기능을 유지하면서 중복 코드를 약 65% 제거
- 리팩토링 이후 pagination 버튼 UI, empty row 높이, 반응형 tooltip, 라이선스 관련 액션 버튼 등 신규 요구사항이 들어올 때마다 공통 계층(`InformationTableFooter`, `BodyWrapper`) 수정만으로 5개 타입 전체에 일괄 반영되는 구조로 개선
